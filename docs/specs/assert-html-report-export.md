# Portable ASSERT HTML report export

## Decision and scope

CAE will retain its existing run viewer. Add an optional **Export ASSERT HTML report** action to a conversation's existing ASSERT semantic review surface. The first slice exports one completed execution conversation with an existing, persisted ASSERT review. It does not embed the upstream SvelteKit viewer or add a second suite/run navigation experience.

The report is a CAE-rendered portable presentation of saved ASSERT results, attributed to ASSERT with its recorded version. It must not claim to be generated by the upstream viewer. Use a small server-side HTML renderer; do not vendor the upstream viewer, add a Node service, upgrade ASSERT, or invoke another evaluation. Follow current repository conventions for export downloads and user/project visibility.

## User behavior

A conversation with a valid saved ASSERT result exposes the export action beside its semantic review controls. The browser downloads a meaningful `.html` filename. Export failures appear in the existing UI error pattern. A conversation without a review cannot export; the UI explains availability without starting a judge automatically. Loading or failed exports must not appear successful.

Opening the file offline displays the run/conversation identity, scenario, target, recorded ASSERT version/model, available provenance, and a clear distinction between CAE's deterministic verdict and the ASSERT semantic assessment. The report includes recorded dimension values, applicability, scales when present, dimension justifications, behavior-node judgments, and the conversation's messages and tool evidence. Preserve actual recorded values; missing fields say unavailable, never invent a score, citation, or tool success. Do not expose credentials, filesystem artifact paths, or unrelated project data.

Use an approachable standalone layout inspired by the viewer's judgment/conversation pairing. Native HTML disclosure elements may expand tools or lengthy evidence. Audio remains in CAE; the report explains when recording evidence is referenced but not embedded. No external scripts, CSS, fonts, requests, or executable transcript HTML. If saved citation anchors can be reliably resolved, provide links to matching evidence; otherwise show the recorded citation as unresolved without guessing. This slice need not build a new citation resolver.

## API and correctness

Provide a read-only download endpoint consistent with the existing ASSERT execution routes, scoped by execution run and conversation IDs. Apply existing run-owner and project-visibility rules before loading/exporting evidence. Wrong owner or inaccessible project returns the repository's non-disclosing not-found response. Nonterminal runs/conversations, missing reviews, malformed results, and stale evidence fingerprints must return an explicit conflict/unavailable response, not a fabricated report. Determine staleness using the existing ASSERT provenance and fingerprint helpers where available.

Render from persisted conversation evidence and review/provenance, not client-supplied scores or arbitrary filesystem paths. The export must not invoke a judge, spend credits, mutate verdicts, or replace the deterministic result. Return `text/html` with an attachment disposition, a safe filename, and private/no-store caching as appropriate. Escape every untrusted value, including transcript, arguments/results, justification, IDs, dimension labels, and metadata. Keep JSON evidence readable. Do not create audio data URLs or serialize the entire raw run object.

## Acceptance evidence

- Focused API tests cover valid output, owner/project isolation, unavailable/nonterminal/stale results, and malicious HTML in transcript/judgment/tool content.
- Verify output contains recorded verdicts and evidence without internal paths or remote dependencies; verify export does not invoke judging or spend credits.
- Browser validation covers action visibility, download success, filename, and useful error handling. Open a saved HTML artifact locally and visually inspect report readability and expanded tool details.
- Run the relevant API tests and web type/lint/build checks required by the repository. Preserve proof and summarize material limitations in the PR.

## Out of scope

Full viewer embedding; new comparisons; suite-level or bulk exports; new judging; copying ASSERT frontend source; new authentication; audio playback/waveforms; a redesign of CAE's run view. Those can be separate decisions after this portable export is reviewed.

## Implemented saved-data contract

The download selects an exact `review_id` under an execution conversation. Pending, applied and superseded saved ASSERT reviews remain exportable when their original evidence is current; the selected assessment and currently applied adjudication are displayed separately. Project access resolves the stored `product_project_id` when available and rejects ambiguous or inaccessible project keys with a non-disclosing 404.

Current reviews persist the semantic result/provenance and hashes, but deliberately remove raw judge output. Export uses those persisted dimensions, scales and behavior judgments and never opens artifact paths. It compares the existing deterministic evidence snapshot and recomputes the upstream judging-input fingerprint with the saved model. Historical reviews omit `judge_n`, so the recorded fingerprint must match one of ASSERT's supported counts (1–3). Missing provenance, invalid values or changed scenario/target/conversation inputs return 409.

This slice shows saved citations as unresolved text because current persisted citations do not carry reliable transcript anchors. Known credential fields/text and internal paths are scrubbed by an export-local sanitizer built on the existing CAE evidence redactor. Audio stays in CAE. The HTML has embedded CSS, native disclosure controls, escaped content and a restrictive CSP; it works offline with no external requests. The web download derives a bounded filename from the three IDs when cross-origin browsers do not expose Content-Disposition.

Synthetic fixture evidence is explicitly labeled and is used only for tests and local screenshots; it does not claim a live ASSERT judgment.
